# T-01 — A new remote pane should open in the focused remote pane's folder

**Status:** OPEN
**Tracker:** `ISSUES.md` — SECTION 1 — PANES
**Artifacts (not committed):** `issues/artifacts/T-01/`

## What was reported

Opening a new remote pane while an existing remote pane is focused starts the
new pane in the default directory instead of the directory the focused pane is
already in. Working three levels deep on a remote machine and wanting a second
shell beside the first means navigating there again by hand.

## Expected

When a remote pane is focused and a new remote pane is opened, the new pane
opens on the same host, in the focused pane's current working directory.

## Notes toward a fix

The remote cwd is already resolved elsewhere and should be reused rather than
re-derived:

- `IssueTrackerStore.remotePaneContexts(host:)` resolves every zmx session on
  a host in a single SSH round trip, precisely to avoid a burst of one probe
  per pane.
- `AgentOverviewPane.workingDirectory(for:)` is the local equivalent.

The hard part is timing, not lookup. A restored remote pane has to recover its
cwd from the shell process that owns the session, because zmx does not replay
Ghostty's `pwd` action — so the cwd can arrive after the pane does. Falling
back to the default directory the moment the cwd is not yet known would make
this fail exactly when panes are being restored, which is when several remote
panes exist at once and the feature matters most.
